| # | 할 것 | 보이는 것 | 말할 것 | 실측 |
|---|---|---|---|---|
| 1 | 앱 홈 -> 결과 탭 | 폴더별 상태(검사 완료, 확인 대기), 메일과 캘린더 연결, 결과: 결정 10건이 바뀌었는데 문서에 남은 옛 값 | "첫 점검은 미리 끝내 두었습니다. 지금부터는 바뀐 곳만 봅니다." | 즉시 |
| 2 | 결과에서 `requirements_backend.md` 의 "서버는 AWS EC2에 배포한다" 열기 | 옛 값, 파일과 줄, 바뀐 결정 "AWS EC2 대신 AWS Lightsail"(10/20 회의) | "모든 지적에 근거가 붙습니다. 파일은 고치지 않고, 고치는 판단은 사람이 합니다." | 즉시 |

| 5 | 확인 질문 탭 열기 | 예, 아니오 질문 목록 | "애매하면 먼저 사람에게 묻습니다." 답은 시연 중에 하지 않음(아래) | 즉시 |

| 7 | 설정 > 점검 수준(정밀, 균형, 절약), 확인 기준 / 홈 > "지금 점검" | 바뀐 것이 없어 바로 끝남, 요청 0회 | "아무것도 안 바뀌면 요청은 0번입니다." | 0.7초, 요청 0회 |

기다리는 동안 할 말: "모델은 바뀐 줄 하나와 그 결정만 받습니다. 나머지 줄은 저장된 판정을 그대로 씁니다."
3단계가 요청 0회인 이유: 리허설에서 같은 문장을 이미 판정해 저장해 두었기 때문이다. 처음 보는 문장이면 1회.

## 열지 말 것 (알려진 오판)

옛 결정이 따로 남아 맞는 줄을 틀렸다고 하는 7줄이다. 질문을 받으면 "실제 모델의 한계"로 설명한다.

- requirements_backend.md "데이터베이스는 PostgreSQL을 사용한다", test_cases_backend.csv "PostgreSQL 연결 테스트"
- requirements_frontend.md "모바일 앱은 Flutter로 개발한다"
- schedule.csv "최종 발표"(이미 11/17)
- api_requirements_memo.docx "사진을 최대 5장까지", tasks_backend.csv "최대 5장 처리", test_cases_ui.csv "사진 5장 업로드"

확인 질문(5단계): 리허설에서 결제 질문에 "예"라고 답하니 2분 동안 요청 22회를 쓰고도 판정이 바뀌지 않았다(QA F06과 같은 한계).
시연 중 답하면 그 사이 7단계의 "지금 점검"이 밀린다. 질문 화면만 보여 주고 "답을 판정에 바로 반영하는 부분은 개선 중"이라고 말한다.
